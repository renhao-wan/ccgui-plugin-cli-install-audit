# CLI 安装检测

CC GUI 设置页插件：探测宿主支持的 CLI 引擎，检查每个引擎的 PATH 入口、运行中进程、版本与 SHA256 是否一致。打开时只做秒级命令发现，选中引擎后才读版本与哈希。

## 为什么需要

CC GUI 支持多个 CLI 引擎，它们各有自己的安装来源：

- **Claude Code** 有 npm 全局安装和 CC GUI 自带的 SDK 副本两条独立升级路径
- **OpenCode**、**Codex** 等通过 npm 或官方安装器落地，可能在不同目录留下多份
- 每个引擎升级时只动自己那份，其他副本不会跟着变

一旦版本错开，同一个引擎在 CC GUI 里和终端里的行为就会不同。这个插件把每个引擎的差异直接摊开：路径、版本、SHA256、运行中实例数与归属。

## 检测的引擎

| 引擎 | 探测命令 |
|---|---|
| Claude Code | `claude` |
| Codex | `codex`、`codex-cli` |
| OpenCode | `opencode` |
| Qoder | `qoder` |
| Qoder (CN) | `qoder-cn` |
| Kimi CLI | `kimi` |
| Grok CLI | `grok` |
| CodeBuddy | `codebuddy` |
| MiniMax | `minimax` |
| OMP | `omp` |
| DSH | `dsh` |
| AGY | `agy` |
| Pi | `pi` |

引擎 id 来自 `ccgui-next.exe` 的 `AgentFrameProviderSection` 枚举；候选命令名参考宿主自带的 CLI 搜索目录（`.codex-cli\bin`、`.omp\bin`、`OpenAI\Codex\bin`、`AppData\Roaming\npm` 等）。

**命令名对不上时只会显示「未安装」，不会误报。** 每个「未安装」的引擎都会把探测过的命令名列出来，方便你对照自己实际装的是什么。

## 检测是怎么分段的

一次全量深度检测要跑十几次 `--version`，还要对每个二进制算 SHA256，实测约 9 秒——打开设置页就等这么久不合理。所以拆成两段：

| 阶段 | 触发 | 耗时 | 做什么 |
|---|---|---|---|
| 恢复缓存 | 打开区块（存在历史结果时） | 毫秒级 | 从 `ctx.storage` 读回上次结果，不跑 PowerShell |
| 命令发现 | 首次打开、点「重新发现」 | 约 1–2 秒 | 只跑 `Get-Command`，列出 13 个引擎里哪些已安装 |
| 深度检测 | 在下拉框选中引擎、点「检测」 | 单引擎约 1–5 秒 | 解析 shim、读 `--version`、算 SHA256、匹配运行中进程 |

切换下拉框即触发该引擎的检测；结果写入 `ctx.storage` 并在会话内缓存，切回来直接显示。「重新检测」忽略缓存重扫当前引擎；「全部检测」串行刷新所有已安装引擎，按钮上显示 `检测中 3/7` 进度。

## 每个引擎检查什么

| 来源 | 怎么拿到 |
|---|---|
| PATH 解析顺序 | `Get-Command <命令> -All`，与 cmd / PowerShell 执行时一致 |
| 运行中进程 | 所有进程的 `ExecutablePath`，按目标文件路径匹配 |
| 进程实例数 | 同一路径的多个进程合并计数，卡片显示「运行中 ×2」 |
| 进程归属 | 回溯父进程链，标出 `CC GUI`、`终端` 或 `其他` |

npm 生成的 `.cmd` / `.bat` shim 会先解析成它实际调用的目标再算哈希：JS bin 解析到 `node_modules` 下的 `.js`（用 `node <script> --version` 读版本），native bin 解析到 `.exe`，避免把 160 字节的包装脚本误判成「另一个安装」。实在解析不出的 shim 会保留并标注「未解析的 shim」，不参与一致性比较。

归属判定是往上找最多 12 层父进程：链上出现 `ccgui` / `codemoss` 归为 CC GUI，出现 Windows Terminal、cmd、PowerShell、VS Code 等归为终端。同一份二进制可能同时被两边使用，卡片会显示 `CC GUI + 终端`。

结论按引擎分别给出：

- **一致** — 该引擎所有入口的 SHA256 相同
- **版本相同，文件不同** — 可能是不同构建
- **版本分叉** — 已存在实质差异
- **无法读取文件** — 找到了入口，但读不到可比较的 SHA256（例如权限不足）
- **未安装** — PATH 里没找到任何候选命令

## 安装与使用

CC GUI 侧边栏「插件」→ 在市场里搜索「CLI 安装检测」，或从本地目录安装。

两个入口：

- **设置页**：设置 → 插件 → CLI 安装检测 → 「CLI 安装检测」区块
- **命令面板**：搜「CLI 安装检测」，直接跳到上面那个区块

进入区块时优先恢复上次结果（毫秒级）；没有缓存才做一次命令发现（约 1–2 秒），列出 13 个引擎里哪些已安装。在下拉框里选中某个引擎后，才读取它的版本、SHA256 与运行中进程。结果写入 `ctx.storage`，切回来或重启 CC GUI 后直接显示。右上角「重新发现」重扫 PATH，并清掉已不存在引擎的旧详情；「全部检测」按顺序刷新所有已安装引擎，不会同时拉起多个 PowerShell。下拉框支持方向键、Home/End、Enter 和 Escape 操作。

## 权限

| 权限 | 用途 |
|---|---|
| `ui:settings-section` | 设置页里的检测区块 |
| `ui:command` | 命令面板入口 |
| `exec:powershell` | 调用 PowerShell 读取进程列表、版本与文件哈希；深度检测会执行 PATH 中探测到的 CLI 的 `--version` |
| `storage` | 经 `ctx.storage` 保存上次检测结果 |
| `network:ccgui-feedback.2653990378.workers.dev` | 「发送反馈」：把你填的那段文字转发到作者邮箱。不点就不会发 |

不读对话内容、不直接写文件系统。唯一写入的是宿主提供的插件键值存储（`ctx.storage`），实际落在 CC GUI 的 `app.db`。
除你主动点「发送反馈」外不发起任何网络请求——插件本身不抓网页、不调第三方 API。

> 为什么需要 `exec:powershell`：插件 SDK 没有文件系统 API，读进程与算 SHA256 只能经宿主授权的子进程完成。PowerShell 是唯一需要的二进制。

## 反馈

设置页底部有「反馈」一区，两种方式任选：

1. **通过 GitHub 提 Issue** —— 打开已经预填好你那段文字的 Issue 页面，
   登录状态下只差一次点击。不需要任何网络权限，永远可用。
2. **发送反馈** —— 经中转直接发到作者邮箱，不用注册、不用跳转。

**发送的内容只有**：你填的那段文字、插件版本、CC GUI 版本、时间戳。
不含会话内容、代码、文件路径或任何本机信息。请求体字段在单测里钉死了白名单
（`test/feedback.test.mjs`），多一个字段就测试失败。

额度是**每台机器每天 30 条，四个插件共享同一个池**（另加 10 分钟 3 条的突发保护），
防止被脚本刷。额度用完时界面会直说，并提示改用 GitHub Issue——不会静默失败。

中转是作者自建的 Cloudflare Worker，凭据只存在它的 secret 里——
插件里没有任何邮件密钥，因为没有密钥可放。**中转的代码是公开的**，
上面关于隐私的每一项承诺都可以自己核对：
[ccgui-feedback-worker](https://github.com/renhao-wan/ccgui-feedback-worker)。

### 发不出去时

`workers.dev` 在国内常被 DNS 污染，邮件中转可能连不上。插件不会卡在那里，
每种失败都给出下一步：

| 情况 | 你会看到 | 还能做什么 |
|---|---|---|
| 网络/DNS 不通 | 连不上反馈服务，请检查网络或代理 | 改用 GitHub Issue |
| 请求超时 | 发送超时。中转可能被网络挡住 | 改用 GitHub Issue |
| 返回 200 但不是中转的 JSON | 反馈服务返回了无法识别的内容，可能被网络拦截 | 改用 GitHub Issue |
| 发得太快（10 分钟内第 4 条） | 发得太快了，稍等几分钟再试 | 稍候，或改用 Issue |
| 今天 30 条用完 | 今天的反馈额度已用完，明天再来 | 明天，或改用 Issue |
| 中转内部出错（5xx） | 中转暂时不可用，稍后再试 | 稍后重试，或改用 Issue |
| 权限没生效（旧版本升级） | 网络权限未生效，请重新安装插件 | 重新「从本地目录安装」 |

第二行这条别忽略：运营商劫持页、校园网登录门户、代理错误页**都会返回 200**。
只看状态码就会告诉你「已发送」，而你实际什么都没发出去。所以判成功要求
响应体里带 `ok: true`，不是 2xx 就算。

**GitHub Issue 那条路不依赖中转**，国内网络下基本总能走通，所以它始终在按钮旁边。

失败时**正文不会清空**，可以直接重试，不用重打一遍。发送期间继续打字也不会
被清掉——成功时只清掉「这次发出去的那段」。

额度查不到时，额度那一行会给出「重试」按钮，不用重开设置页。

## 数据存在哪里

检测结果写在 `ctx.storage` 的 `audit-cache-v1` 键下：

```js
{
  version: 1,            // 结构版本，不匹配就丢弃
  engines: [...],        // 上次命令发现结果
  details: {             // 按引擎分开存取
    claude: { engine: {...}, at: "2026-11-18T06:32:10.000Z" },
    ...
  },
  savedAt: 1763447530000
}
```

- **重启 CC GUI 后**直接显示上次结果，不重跑 PowerShell
- 每个引擎的结果独立标注「检测于 …」，不会把旧数据当成当前状态
- 「缓存于 …」只在写入成功后显示；存储失败时自动降级为纯内存缓存
- 点「重新检测」才刷新，发现结果用「重新发现」刷新
- 存储不可用时静默降级为纯内存缓存，功能不受影响

## 已知限制

- 仅 Windows（依赖 `Win32_Process`）。
- 深度检测按引擎串行执行：版本探测与 SHA256 都在同一个 PowerShell 进程里顺序完成，单个引擎约 1–5 秒。
- 进程按可执行文件**路径**分组，同一路径跑 N 个实例只显示一个文件、标「×N」。
- `--version` 有 4 秒超时；不支持的 CLI 会显示「版本未读取」，但仍会比较哈希。
- 部分引擎的候选命令名来自推断，可能与本机实际安装名不同，此时显示「未安装」。
- npm 的 JS bin 会解析到目标 `.js` 并参与哈希比较，但进程统计按可执行文件路径匹配，这类入口不会显示运行中实例数。
- 解析失败的 `.cmd` / `.bat` 会保留为「未解析的 shim」，其哈希不参与一致性判断。
- 引擎清单是静态表（`main.js` 顶部的 `ENGINES`）。宿主新增引擎时需要发版才能覆盖：`ctx.models.listEngines()` 能给出宿主的引擎目录，但不提供可执行文件名，PATH 检测仍依赖命令名映射。
- Qoder 与 Qoder (CN) 共用 `qoder` 命令时只会识别为 Qoder，不重复计数。
- 归属依赖父进程链，链被提前终止（如以服务方式启动）时可能归为「其他」。

## 兼容性

- 实测环境：Windows 11、CC GUI 1.2.4、插件 SDK 0.3.26。
- `manifest.json` 的 `minAppVersion` 保持 `1.0.4`；`ctx.storage` 不可用时自动降级为纯内存缓存，`ctx.ui.openSettings` 不可用时命令面板入口会失效，但设置页区块仍可正常使用。

## 开发

```bash
node scripts/check-feedback-sync.mjs  # 反馈纯函数与基准（github-trending/src/lib/feedback.mjs）逐字一致
node scripts/validate-manifest.mjs
node scripts/smoke.mjs               # 反馈区（其余部分需真机 PowerShell，见「已知限制」）
```

自检同时校验 `manifest.permissions` 与 `main.js` 中实际用到的能力是否一致（例如 `ctx.storage` 必须有 `storage` 权限），避免运行期静默失败。

发版：升 `manifest.json` 的 `version`，打同名 tag（无 `v` 前缀），Release 由 Action 生成。
